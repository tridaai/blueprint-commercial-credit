# Blueprint — Commercial Credit Memo & Covenant Monitoring Agent

A working prototype of the deployment a bank's commercial lending
team needs around an AI model: a credit application arrives, borrower
financial statements in inconsistent formats must be spread into the
bank's template, ratios computed, lending policy tested, a memo
drafted for committee, and — after closing — covenants re-tested on
schedule from fresh financials instead of stale ones.

This blueprint builds that pipeline under one rule the whole design
hangs on: **the model never computes a number.** Every figure is
either read from a borrower document with a pointer to its page and
line, or — in later rounds — computed in code from figures that
were. The agent assembles, drafts and monitors; **the credit officer
and the credit committee decide.** Nothing in this system approves
credit.

This is an independent Trida AI blueprint. It is **not affiliated
with or endorsed by any bank or vendor named in its research**; it
is built by Trida AI against public patterns to show how a
forward-deployed team would put an agent into production inside a
commercial lending operation.

> **Work in progress** — this blueprint is built and passing its automated test and eval gates, but it has not yet finished hands-on local testing, and its companion blog post is not yet published. Expect changes. This notice comes off when both are done.

## Try it in 3 commands

```bash
uv sync --extra dev
uv run commercial-credit-demo     # traced end-to-end run, offline
uv run pytest -q                  # the test suite
uv run python evals/run_evals.py  # the eval gate
```

The demo opens the sample application (a mid-market manufacturer
seeking a term loan), generates its document checklist, files three
years of financial statements, and extracts every statement figure —
each printed with the document, page and line it came from.

## What round 1 builds

The pipeline spine and the evidence discipline everything else
hangs on:

- **Credit file model** — borrower, guarantors, facility request,
  and the file's status, behind a store port (PostgreSQL in a
  deployment; SQLite locally; in-memory doubles in tests).
- **Application intake** — an LOS port with a reference feed; open
  an application inline or by origination-system reference.
- **Document checklist, generated by facility type** — term loans,
  revolvers, CRE, construction, equipment and SBA 7(a) each get the
  base file plus their own required documents (appraisal and rent
  roll for CRE; borrowing-base pack for revolvers; SBA forms for
  7(a)…). Every item cites the policy rule that required it.
- **Document intake with hashes** — borrower documents are stored
  through an S3-compatible port; their SHA-256 is recorded at
  intake, and every later read re-verifies the bytes against it.
- **Provenance-carrying extraction** — an extraction port whose
  contract requires every value to carry its document, page and
  line/cell. A value without complete provenance is rejected whole
  batch, in code, with tests proving the rejection. The offline
  reference extractor reads the generated borrower documents and
  returns real coordinates into the stored bytes.
- **Audit log, structured JSON logs with request ids, `/health`
  and `/readiness`** — the readiness payload names the live store
  profile so a test double is never mistaken for the real store.

Later rounds add the spreading engine, the deterministic ratio and
covenant computation engine, the versioned policy pack, cited memo
drafting with a figure verifier, the credit-officer and committee
gates with coded adverse-action reasons, and the covenant monitoring
loop. The round map is in `docs/architecture.md`.

## The laws (enforced in code, never in prompts)

1. **No model-computed numbers.** Extraction returns values +
   provenance; all math is deterministic code. A memo figure that
   traces to neither is rejected by the memo verifier.
2. **Policy is code, versioned.** Each memo records the policy
   version it was tested under.
3. **Adverse decisions carry coded reasons** (ECOA/Reg B: specific,
   accurate reasons — a model paraphrase is not a reason).
4. **Two human gates** — credit officer, then committee; the
   preparer cannot be the sole approver.
5. **Spreading disagreements surface, never average out** — audited
   vs management vs tax-return figures are all carried, with the
   disagreement named in the memo.
6. **Covenants are clocks + math** — structured test dates and
   thresholds; detection is the agent's job, waiver and enforcement
   are the bank's.
7. **Stale inputs block, visibly** — a memo cannot be marked
   committee-ready over a stale or missing required input; the
   block names the item.
8. **Every draft edit is evidence** — draft-vs-final diffs are
   recorded; the record shows what the machine proposed and what
   the human changed.

## Configuration

| Variable | Meaning |
| --- | --- |
| `DATABASE_URL` | Postgres DSN. Set ⇒ Postgres profile (migrations run at startup). Unset ⇒ local SQLite store. |
| `CREDIT_SQLITE_PATH` | SQLite file for the local profile (default `./data/credit.db`). |
| `S3_ENDPOINT_URL` | S3-compatible endpoint (the compose stack's SeaweedFS at `http://minio:8333`). |
| `S3_BUCKET` | Document bucket. Unset ⇒ in-process local document store. |
| `S3_REGION` | Default `us-east-1`. |

## Honest status

- Live verification of the Postgres profile and of the S3 document
  store runs in the production-profile round; round 1's gates run
  against the SQLite and in-memory doubles behind the same ports.
- Document extraction is the offline reference extractor over the
  generated borrower documents; a document-AI adapter slots behind
  the same port in a deployment and inherits the same provenance
  contract. No claim is made about scanned PDFs today.
- There is no real LOS or core-banking integration — ports and a
  reference feed only.
- The sample borrower book is generated for this blueprint, with
  figures known by construction so extraction can be graded against
  ground truth; that is the repo's one data note.
