# Blueprint — Commercial Credit Memo & Covenant Monitoring Agent

A working prototype of the deployment a bank's commercial lending
team needs around an AI model: a credit application arrives, borrower
financial statements in inconsistent formats must be spread into the
bank's template, ratios computed, lending policy tested, a memo
drafted for committee, and — after closing — covenants re-tested on
schedule from fresh financials instead of stale ones.

This blueprint builds that pipeline under one rule the whole design
hangs on: **the model never computes a number.** Every figure is
either read from a borrower document with a pointer to its page and
line, or — in later rounds — computed in code from figures that
were. The agent assembles, drafts and monitors; **the credit officer
and the credit committee decide.** Nothing in this system approves
credit.

This is an independent Trida AI blueprint. It is **not affiliated
with or endorsed by any bank or vendor named in its research**; it
is built by Trida AI against public patterns to show how a
forward-deployed team would put an agent into production inside a
commercial lending operation.

> **Work in progress** — this blueprint is built and passing its automated test and eval gates, but it has not yet finished hands-on local testing, and its companion blog post is not yet published. Expect changes. This notice comes off when both are done.

---

## Try it in 3 commands

```bash
uv sync --extra dev
uv run commercial-credit-demo     # traced end-to-end run, offline
uv run pytest -q                  # the test suite
uv run python evals/run_evals.py  # the eval gate
```

The demo opens the sample application (a mid-market manufacturer
seeking a term loan), generates its document checklist, files three
years of financial statements, and extracts every statement figure —
each printed with the document, page and line it came from.

## What round 1 builds

The pipeline spine and the evidence discipline everything else
hangs on:

- **Credit file model** — borrower, guarantors, facility request,
  and the file's status, behind a store port (PostgreSQL in a
  deployment; SQLite locally; in-memory doubles in tests).
- **Application intake** — an LOS port with a reference feed; open
  an application inline or by origination-system reference.
- **Document checklist, generated by facility type** — term loans,
  revolvers, CRE, construction, equipment and SBA 7(a) each get the
  base file plus their own required documents (appraisal and rent
  roll for CRE; borrowing-base pack for revolvers; SBA forms for
  7(a)…). Every item cites the policy rule that required it.
- **Document intake with hashes** — borrower documents are stored
  through an S3-compatible port; their SHA-256 is recorded at
  intake, and every later read re-verifies the bytes against it.
- **Provenance-carrying extraction** — an extraction port whose
  contract requires every value to carry its document, page and
  line/cell. A value without complete provenance is rejected whole
  batch, in code, with tests proving the rejection. The offline
  reference extractor reads the generated borrower documents and
  returns real coordinates into the stored bytes.
- **Audit log, structured JSON logs with request ids, `/health`
  and `/readiness`** — the readiness payload names the live store
  profile so a test double is never mistaken for the real store.

## What round 2 adds

The spreading engine — the deterministic heart of the workflow:

- **The bank's template as data** — a standard line taxonomy for the
  balance sheet, income statement and cash-flow statement
  (`spreading.py`); every extracted value is mapped onto its template
  line by field, across all periods at once.
- **Unmapped lines are carried, never dropped** — a statement line
  the taxonomy does not map enters the spread as a named unmapped
  entry, with its values and provenance, instead of vanishing or
  being silently folded into a line it does not belong to.
- **Multi-period spreads** — FY2022–FY2024 for the sample borrower,
  built end to end from the round-1 extractions, with
  period-over-period change data per line. Money is Decimal
  throughout, and the build is deterministic: the same extractions
  and adjustments rebuild the same spread byte for byte, under the
  same content-derived spread id.
- **Adjustments as first-class records** — an add-back names the
  spread line and period, its amount, a coded reason *and* a
  free-text reason, the document provenance that justifies it, and
  who proposed it. An adjustment missing any of those is rejected.
  The unadjusted view is never touched; the adjusted view is derived.
- **Restatements supersede cleanly** — when a corrected statement
  version is filed for a period, the spread for that period rests on
  the new version and records it (document, SHA-256, version number);
  the superseded extraction stays in the store, retrievable.

## What round 3 adds

The deterministic computation engine — every number a credit
officer will ever quote, computed in code from the spread:

- **The full ratio set, defined in writing** — liquidity (current
  and quick ratios, working capital), leverage (funded debt,
  debt/EBITDA, liabilities over tangible net worth), coverage
  (DSCR, fixed-charge coverage), profitability (margins, ROA, ROE)
  and cash flow (operating cash flow, free cash flow, cash
  conversion). Debt service is spelled out: scheduled principal —
  the prior period's current portion of long-term debt — plus
  interest, plus capital lease payments when a provenanced figure
  for them is supplied.
- **EBITDA with its working shown** — operating income plus
  depreciation & amortisation, on the adjusted view, with the R2
  adjustments it rests on named in the derivation.
- **Derivation traces, mechanically verified** — every figure is a
  chain of recorded steps whose inputs name the spread line, the
  period and the extraction provenance behind the cell. A verifier
  walks the chains and re-performs the arithmetic; the eval gate
  requires 100% trace completeness.
- **Global cash flow** — borrower and guarantors combined, with
  eliminations as named, reasoned records (intercompany rent,
  intercompany debt service). A guarantor with no spread is refused
  entry to the combined view unless the caller explicitly excludes
  them — and the exclusion is recorded on the pack.
- **Covenant headroom against given definitions** — metric,
  operator, threshold and period supplied to the run; the result
  states the value, the headroom and whether the historical figures
  comply. (Storing covenants and scheduling their tests is round
  10; the policy pack is round 4.)
- **Computation packs as stored artefacts** — a pack is
  content-addressed: recomputing the same spread with the same
  supplemental figures and definitions returns the identical pack,
  byte for byte. A figure whose inputs are absent is recorded as
  *not computable*, naming what is missing — nothing is zero-filled
  or estimated. The sample borrower's statements carry no
  cash-flow page, so its EBITDA and cash-flow figures say exactly
  that, naming depreciation & amortisation as the missing input.

Later rounds add the versioned policy pack, cited memo drafting
with a figure verifier, the credit-officer and committee gates with
coded adverse-action reasons, and the covenant monitoring loop. The
round map is in `docs/architecture.md`.

## What round 4 adds

The policy pack — lending policy as versioned code (design law 2),
run against every credit file the pipeline opens:

- **Eight coded tests, each citing the policy it encodes** —
  maximum leverage by borrower segment (total liabilities over
  tangible net worth), minimum DSCR for the borrower and, where
  owners guarantee the facility, for the combined global view,
  minimum fixed-charge coverage, maximum single-borrower
  concentration against the bank's stated capital base,
  required-documents completeness by facility type (the round-1
  checklist), and age limits on the financial statements and on
  appraisals. Each test names the exact inputs it reads — a
  computation figure, or a fact of the credit file — and its
  severity: blocker or warning.
- **A third outcome, stated plainly** — besides pass and fail, a
  test can be *not evaluable*: its input figure could not be
  computed, no global pack was combined, the document it ages is
  not on file. The outcome names the missing input. A DSCR the
  statements cannot support is never a silent pass — the sample
  borrower's report says exactly that, naming depreciation &
  amortisation. The eval gate re-checks every figure-test pass
  against the pack it read; the silent-pass counter is required
  to be zero.
- **Version discipline** — evaluating a file pins ONE pack version
  and records it in the file's policy history; the report is a
  stored, content-addressed artefact (re-evaluating unchanged
  inputs reproduces it byte for byte). Two versions ship: v2
  tightens the minimum DSCR to 1.35×, the hospitality leverage
  ceiling to 1.75×, and the statement-age limit to 15 months. A
  borrower at exactly 1.30× passes v1 and fails v2 — and its v1
  report stays on the record, untouched, because a policy change
  never silently re-judges an in-flight credit.

Later rounds add cited memo drafting with a figure verifier, the
credit-officer and committee gates with coded adverse-action
reasons, and the covenant monitoring loop.

## What round 5 adds

Memo drafting — and the figure verifier that decides whether a
draft may exist at all:

- **A structured draft memo, pinned to its sources** — a stored,
  content-addressed artefact (migration 0005) whose header pins
  the spread, the computation pack, the policy pack and version,
  the policy report and its as-of date, all by id. Sections:
  request summary, borrower overview, financial analysis
  (per-period narrative plus spread and computed-measures
  tables), strengths, risks and mitigants, policy exceptions,
  and placeholders for the recommendation and the conditions —
  the memo states facts and policy outcomes; the recommendation
  is the credit officer's to make, at the gate in round 6.
- **The figure verifier (design law 1, enforced on prose)** —
  before a memo can be stored as a draft, every numeric figure
  in its final rendered text and tables is extracted and traced:
  it must equal a figure in the pinned computation pack, a
  spread line value, a policy threshold or outcome value, or a
  stated fact of the credit file. One untraceable figure — a
  number altered by a cent, a transposed ratio, a figure
  invented out of thin air — and the memo is refused storage,
  with the offending figures named. The traces that cleared are
  stored with the memo as its verification record, so any figure
  a reader questions can be walked back to its artefact and
  field through the API.
- **Exceptions that cannot be dropped or softened** — the
  exceptions section must account for exactly the pinned
  report's non-pass outcomes, by test id: every blocker fail and
  every not_evaluable, carried in full. The check is structural,
  in the verifier, so a draft that omits one — or rewrites a
  not_evaluable as a pass — is refused even if every figure in
  the doctored text still traces.
- **Drafting behind a profile port** — the default `offline`
  profile is a deterministic composer that assembles the
  narrative from the structured artefacts and invents nothing
  (the eval gate property-checks that across the fixtures); a
  `live` profile is defined behind the same port for a
  model-backed drafter, not configured until provider-key
  handling lands. Whichever profile drafts, the verifier — not
  the drafter — decides whether the memo may be stored.

Later rounds add the committee gate with coded adverse-action
reasons, and the covenant monitoring loop.

## What round 6 adds

The credit officer gate — the first human gate, where the draft
memo is decided by a named person, and every edit they make is
evidence:

- **Named officers, or nobody acts** — every gate action records
  who acted and in what role. Submitting a draft for review is
  open to any named actor; approving, returning and flagging
  require a credit officer role (credit officer, senior credit
  officer, chief credit officer). An anonymous or role-less
  action is refused mechanically, before anything else is
  looked at.
- **Approval mints a new artefact** — the officer approves as-is
  or with paragraph edits to the narrative sections (the
  recommendation and conditions placeholders are theirs to
  complete). Approval never edits the draft in place: it stores
  an officer-final memo — status `officer_approved`,
  committee-ready — naming the draft it supersedes and the
  officer who approved it. A memo's live review status (draft /
  in review / returned / approved) is derived from its recorded
  review events (migration 0006), never stored on the artefact.
- **Edits face the verifier again** — an edited memo is a
  candidate until the round-5 figure verifier has cleared the
  full edited text: one untraceable figure refuses the approval
  and stores nothing. The policy exceptions section is locked at
  this gate — it renders the pinned policy report verbatim, so
  no exception can be dropped or softened by editing it; the
  officer discusses exceptions in the risks section instead.
- **Every approval records its diff** — a `MemoDiff` stores the
  section-level changes (paragraphs before/after) and the
  figure-level changes (figures added, removed, or altered in
  place, each with the artefact + field it traced to on its
  side). An approval as-is records an empty diff — "the officer
  changed nothing" is itself on the record.
- **Returns are coded, and returns reopen nothing** — a return
  for rework names reasons from a versioned vocabulary
  (`officer-return-reasons-v1`); a note may ride alongside but
  never substitutes for a code, and the vocabulary version is
  recorded on the return. A returned memo cannot be approved or
  resubmitted — it is recomposed into a new draft version that
  supersedes it, and the officer who returned it may decide the
  recomposition.
- **Flags the committee will see** — an officer may flag an item
  for committee attention (the flags ride onto the officer-final
  memo at approval), or declare a conflict of interest — which
  bars that officer from approving the memo, by name of the
  flag, so a different officer must decide.

## What round 7 adds

The committee gate — the second human gate, where the credit
itself is decided, and where a decline must explain itself in
codes tied to evidence (design law 3):

- **A quorum of named members, or no decision** — a decision is
  a stored record (migration 0007) naming the members who made
  it, each with a role, the quorum they met, and the recorder —
  who must be one of the members. The quorum is at least two,
  mechanically: a quorum of one is refused whatever the caller
  asks, so the officer who approved the memo can sit on the
  committee but never be its only member, and no preparer-side
  role sits at all. The committee acts only on the
  officer-final memo, only once it stands convened, and a
  decided memo cannot be decided again.
- **Outcomes, all coded** — approve, approve with conditions,
  decline, defer. Each outcome carries only its own payload: an
  approval records no conditions and no reasons; anything else
  is refused rather than quietly stored.
- **Conditions are structured records** — a financial covenant
  (metric, operator, threshold), a reporting requirement, a
  documentation item, each with its due/review cadence as data.
  A covenant's threshold must trace into the memo's pinned
  artefacts through the same trace universe the figure verifier
  uses, and the trace is recorded on the condition — an invented
  threshold refuses the whole decision. Round 10 will schedule
  these as covenants; this round records them.
- **Declines carry coded reasons, tied or refused (law 3)** —
  every adverse-action reason is a code from the versioned
  vocabulary (`adverse-action-reasons-v1`) PLUS a mechanical
  tie: a policy test of the memo's pinned report that failed or
  could not be evaluated (by test id), a figure in the memo's
  verification record (by its trace), or a required checklist
  item missing from the file (by item id). A reason citing a
  test that PASSED, a figure that was never traced, or a
  document that is on file is refused, with the offender named;
  a code wearing the wrong evidence — a coverage "failure" over
  a test that merely could not be evaluated — is refused the
  same way. There is no free-text reason field. The
  borrower-facing adverse-action notice is then GENERATED from
  the codes and their ties — statements from the vocabulary,
  evidence clauses read off the pinned report, the verification
  record and the checklist — so the notice can only say what
  the record already proves (ECOA/Reg B: specific, accurate).
- **Deferrals name the path back** — a deferral carries coded
  reasons (`committee-deferral-reasons-v1`) and named
  re-presentment requirements. The memo's derived status reads
  `deferred`: it is back with the credit officer, it is not a
  draft, and re-presentment convenes the committee again on the
  same officer-final artefact — the new decision supersedes the
  deferral on the record, which keeps both.
- **Status is still derived, never stored** — the officer
  gate's event stream extends with `committee_convened` and
  `committee_decided`, so one ordered record derives the full
  chain: draft → in_officer_review → officer_approved →
  in_committee → committee_approved |
  committee_approved_conditional | declined | deferred.

Round 9 gates this transition on committee readiness (below);
later rounds add the covenant monitoring loop that schedules
round 7's conditions.

## What round 8 adds

Disagreement handling — design law 5 made mechanical. A
borrower's figures arrive from more than one kind of source, and
the kinds do not always agree; this round is the discipline for
that, end to end:

- **Sources are typed, and the types never merge** — every
  extracted value is stamped with its source type (audited
  statements, tax return, management statements). Supersession —
  round 2's restatement rule — now runs *within* a source type:
  a corrected audited statement replaces the earlier audited
  statement. A tax return filed later supersedes nothing; it
  stands beside the audit as a different witness. The spread
  records the current document version per (period, source
  type), so both witnesses stay retrievable as reported.
- **Precedence without concealment** — the spread's working
  figure follows a stated precedence in a versioned disagreement
  policy (`aldergrove-disagreements` v1): audited first, then
  tax, then management. Where two source types report different
  figures for a line beyond the policy's tolerances — exact-zero
  tolerance between the audit and the tax return on revenue,
  EBIT and net income, a 0.1% relative tolerance elsewhere — the
  spread records a **Disagreement**: the line, the period, every
  source's value with its full provenance (document, SHA,
  page/line), the absolute and relative delta of each from the
  working figure, and a materiality verdict (material at 2% of
  the figure or $50,000). The record is part of the spread's
  content, so the spread id covers it. Nothing is averaged, ever:
  on the seed borrower's FY2024 revenue the three witnesses
  report $12,374,000 / $11,905,000 / $12,410,000, and the spread
  carries $12,374,000 — the audited figure — with all three on
  the record.
- **Figures over contested lines are flagged** — the computation
  engine (now `aldergrove-compute-v2`) walks each figure's
  derivation: a figure that reads a materially disagreed line —
  directly, through an intermediate step, or through a figure it
  consumes — carries the disagreement's id on its own record,
  including across the global pack's entity boundary. The figure
  still computes, from the precedence value; it can never present
  as clean, because the memo figure verifier's trace for a
  flagged figure names the disagreement it rests on. Figures
  over lines whose only disagreements are immaterial are not
  flagged: the distinction is the policy's, applied in code.
- **The memo carries them, structurally** — when the spread
  records disagreements, the memo gains a *Document
  disagreements* section: every material disagreement stated in
  its record's own terms (each source's figure, the deltas, the
  verdict), rendered by one canonical function the verifier
  requires verbatim. The verifier checks the section's id list
  against the spread's material set exactly — the same
  discipline round 5 applied to policy exceptions — so a memo
  that drops the section, omits a material disagreement, lists
  an immaterial one as material, or rewords a material
  difference into smaller language is refused, the omission
  named. Immaterial disagreements are counted in the section
  and listed in full through the API. The section is locked at
  the credit officer gate, like the exceptions section: the gate
  cannot soften what the spread recorded.
- **The seed borrower gains its other witnesses** — Hartline's
  FY2024 tax return (revenue $469,000 under the audit, EBIT
  $219,200 under) and management accounts (a touch higher),
  grading detection exactly: seven disagreements, five material,
  two immaterial, and none on the lines where the witnesses
  concur. New API surface: `GET
  /applications/{id}/disagreements` (list, `?material=`
  filter) and `GET /applications/{id}/disagreements/{id}`
  (detail); the spread view carries the records and the
  per-type period sources. No migration was needed:
  disagreements are content of the spread artefact, stored in
  its payload like the packs and memos.

## What round 9 adds

Committee readiness — design law 7 made mechanical. A memo may
be impeccable and its file still unfit for the committee: a tax
return missing, statements gone stale, a figure the computation
could not produce. This round is the engine that says so, in one
place, before anyone convenes:

- **One consolidated ReadinessReport** — a content-addressed,
  stored artefact (migration `0008`) listing every required
  input for the file's facility type with its state:
  `present_fresh`, `present_stale` (with the age and the limit it
  breached), `missing`, or `not_evaluable_input` (a figure the
  computation needs that is not computable, naming the missing
  source input). Three requirement sources are consolidated, not
  listed separately: the round 1 policy-cited checklist, the
  round 4 policy pack's statement-age and appraisal limits, and
  the computation pack's not-computable figures — each entry
  linked to the policy tests that read it.
- **Freshness rules are data** — statement age reads its limit
  from the pinned policy pack's `financial_statement_age` test
  (18 months under v1, 15 under v2 — the same file reads
  differently under each, from the pack, never from a constant);
  appraisals read the pack's `appraisal_age` limit; insurance
  certificates (12 months), tax returns (18) and interim
  statements (6) carry theirs in a versioned readiness policy
  (`aldergrove-readiness` v1). A policy test that *fails* is not
  a blocker — it is credit judgment, carried as a memo exception.
  A test that does not apply to the file at all (a global test on
  an unguaranteed facility) is not entered either. Figure gaps
  block for the pack's latest fiscal period — the period the
  tests and the memo read; an earlier period's gap (the first
  year's debt service needs a pre-window year the checklist does
  not require) is recorded with its missing input named, and does
  not block.
- **The block** — the round 7 convene action recomputes
  readiness at convene time, over the memo's pinned artefacts and
  the file as it stands, and refuses while any blocker stands.
  The refusal **names every blocker** — key, label, state,
  detail — and the API surfaces that text in the 422 body. A
  report minted earlier cannot bless the convene: computed
  fresh-at-2026, the same file is refused at 2028 when its
  statements have aged past the limit. Officer approval (round
  6) still lands on a blocked file — but the approval event and
  the MemoDiff carry the readiness report id and blocker count,
  so the block is on the record from that moment, never a
  surprise at convene.
- **No waivers** — a blocker clears only when the input itself
  refreshes: a new appraisal received makes the stale-appraisal
  blocker clear, and nothing else does. There is deliberately no
  override flag, no note-waiver, no waive method anywhere in the
  codebase — the tests and evals prove the surface does not
  exist (a caller passing a waiver keyword is refused by the
  signature itself). The only exception path remains the
  committee's own conditional approval or deferral (round 7) —
  a credit decision about a *ready* file, never a readiness
  override.
- **The borrower-facing list** — the report renders the named
  outstanding-items list an RM would send ("Business tax
  returns: not on file."), generated from the blocker entries,
  never hand-typed, so the ask can never drift from the block.
  New API surface: `GET /applications/{id}/readiness-report`
  (current, computed at `?as_of=`), `GET
  /applications/{id}/readiness-reports[/{report_id}]`, and `GET
  /applications/{id}/outstanding-items`.

## What round 10 adds

The covenant model and scheduler — design law 6: covenants are
clocks + math. An approval is not the end of a credit's life; it
is the start of its monitoring life, and this round builds the
structure that life runs on:

- **The covenant set** — created in the same act as a committee
  approval (plain or conditional; a decline or deferral creates
  none), from two sources kept visibly distinct: the decision's
  own financial-covenant conditions (thresholds already traced at
  the round 7 gate) and the policy pack's standard template for
  the facility type — a leverage ceiling tested quarterly, a DSCR
  floor tested annually, a liquidity floor — defined as data with
  its policy citations. Where a condition and the template name
  the same test, the committee's term governs and the template
  entry is not duplicated. A condition whose cadence the
  scheduler cannot read as quarterly, semiannual or annual
  refuses the decision before anything is stored: a covenant that
  cannot be scheduled is never quietly dropped from monitoring.
  The set pins the memo's policy pack version and the decision id
  it came from (migration `0009`).
- **The closing anchor** — test dates derive from the facility's
  closing date, a recorded file fact (`POST
  /applications/{id}/closing`, by a named actor, audited; a
  changed date is a named correction, never a silent edit). A set
  created before the closing is recorded stands in the named
  `awaiting_closing_date` state: its covenants exist, its
  schedule waits — no anchor is ever guessed.
- **The schedule, derived in code** — pure date arithmetic over
  the closing date and the term, `as_of` always passed in, no
  wall clock: fiscal period ends at each covenant's cadence
  (month-lattice arithmetic, so leap years and fiscal-year
  offsets land exactly), capped at maturity, with a final
  point-in-time test at maturity itself. Reporting-requirement
  conditions ride the same schedule as dated deliverables (annual
  statements due 90 days after fiscal year end). Every instance
  stands in a derived state — `scheduled` / `due_soon` / `due` /
  `overdue`, or `awaiting_inputs`, naming the exact spread inputs
  the test needs (a fiscal test whose period is not yet spread
  cannot be run, and says what it is waiting for).
- **The scheduler + the queue** — an idempotent tick (`POST
  /covenant-scheduler/tick`) records each instance's first
  sighting at due or overdue on the credit file's audit trail;
  re-running it records nothing twice. The due-work queue (`GET
  /covenant-due-work?as_of=`) answers the monitoring question
  across the portfolio: what is due, for which borrower, needing
  which inputs.
- **Amendment by supersession** — a covenant's threshold,
  operator, frequency or grace is never edited. An amendment
  mints the next version of the covenant with a named author in
  an amending role, a coded reason from the versioned vocabulary
  (`covenant-amendment-reasons-v1`), and the committee decision
  that authorised it; the stored set is byte-identical before and
  after, and tests prove no in-place mutation surface exists on
  the pipeline or any store. New API surface: `GET
  /applications/{id}/covenant-sets[/{set_id}]`, `GET
  /applications/{id}/covenant-schedule?as_of=`, `GET
  /applications/{id}/covenant-amendments`, `POST
  /applications/{id}/covenants/{covenant_id}/amendments`.

## What round 11 adds

Covenant test execution and breach cases — the math half of
design law 6. Round 10 derived the schedule; this round runs the
tests on it, and gives a failure the workflow object a bank
actually works:

- **Test execution through the existing engines** — when a
  covenant test instance is due and its period's statements are
  on file, the test re-spreads the period through the round 2
  spreading engine and recomputes the covenant's metric through
  the round 3 computation engine: no new math lives in this
  round. The figure is read out of the stored computation pack's
  own covenant result and compared against the covenant's
  threshold with the covenant's operator. The outcome is recorded
  as a `CovenantTestResult` artefact — instance, covenant
  id+version, spread id, computation pack id, figure, threshold,
  outcome, as-of — content-addressed and insert-once (migration
  `0010`), so re-running a test over the same inputs stores
  nothing twice and the tick can run as often as the bank likes.
- **Honest outcomes** — `pass` / `fail` / `not_evaluable` /
  `awaiting_inputs`, and no fifth state. A test whose statements
  have not arrived stands at `awaiting_inputs`, recorded with
  the exact inputs it is waiting for — blocked on the borrower,
  never silently skipped. A test whose figure cannot be computed
  (the statements arrived without the cash-flow page, say) is
  `not_evaluable`, naming the missing input; a `not_evaluable`
  never reads as a pass and opens no breach — nothing has been
  measured.
- **Breach cases** — a failing test opens its `BreachCase` in
  the same act, so a failure without a case cannot exist: one
  breach per failing result, carrying the covenant, the figure,
  the threshold, and a cure deadline (test date + the covenant's
  cure period). The state machine runs `open → under_review →
  cured / waived / escalated / defaulted_path`, and every move
  is a coded act by a named officer in a breach role, appended
  to the case's event history and the audit trail: **cured**
  only by a later passing re-test of the same covenant, linked
  by result id (the failing result cannot cure its own breach);
  **waived** only on the authority of a stored committee
  decision of the same credit file with an approval outcome — a
  waiver that names no decision, an invented one, or a decline
  is a free-text waiver and is refused; **escalated** and
  **defaulted** under coded reasons from the versioned
  vocabulary (`breach-resolution-reasons-v1`), the default path
  reachable only through review or escalation. Cured, waived
  and defaulted are terminal and refuse every further act.
  There is no delete and no silent close: an unworked breach
  stays open, ageing against its cure deadline on every list.
- **Restated-input discipline** — every result pins the period
  sources it rested on (the exact document versions of the
  tested period). When the borrower restates that period, the
  result's standing derives as `superseded_by_restatement` —
  flagged at read time, never rewritten — a re-test is
  scheduled and run against the restated figures, and the new
  result supersedes the old by id; the original record, and any
  breach it opened, stand.
- **Portfolio surface** — the scheduler tick now also executes
  due tests and reports what it recorded and opened. API:
  `POST /applications/{id}/covenant-tests/run`, `POST
  /applications/{id}/covenant-tests/{instance_id}/run`, `GET
  /applications/{id}/covenant-test-results` (each with its
  restatement standing), `GET
  /applications/{id}/covenants/{covenant_id}/history`, `GET
  /breach-cases?as_of=` and `GET
  /applications/{id}/breach-cases[/{breach_id}]?as_of=` (with
  ageing: days in breach, days to the cure deadline), and the
  resolution actions `POST
  /applications/{id}/breach-cases/{breach_id}/review|escalate|cure|waive|default`.

## What round 12 adds

The committee's approval starts a clock, and this round builds
the machinery that keeps it: the **annual review**. Every
approved facility with a covenant set owes a review twelve
months after closing — or after approval, when no closing is
recorded, with the basis named on the schedule, never silently
guessed — and annually to maturity. The instances are derived
in code from the anchor (month-lattice arithmetic: a leap-day
closing reviews on Feb 28 in common years, Feb 29 in leap
years), carry the states `scheduled / due_soon / due /
overdue / completed`, join the covenant due-work queue, and
are opened by the scheduler tick idempotently. A late review
never pushes the next one out; each instance derives from the
anchor.

The **review pack** is a content-addressed artefact assembled
in code from stored artefacts only — nothing is spread or
computed by hand. The spread is rebuilt and the figures
recomputed through the existing engines on the latest
statements, the covenant test history for the period is carried
with its restatement standing, every breach of the period and
every open breach ride along with their resolution state, and
material disagreements carry exactly as round 8 left them.
Policy is run **twice**: under the version the decided memo
pinned and under the current version, with every per-test
difference surfaced on the record — a tightening pack never
silently re-bases the file's history. Readiness is recomputed
at the review date, and a pack whose required inputs are stale
or missing is still produced — marked **incomplete**, naming
every blocker. Absence is named, never papered over.

The officer-facing **review summary** follows the house
discipline: the facts are locked paragraphs rendered by code
from the pinned artefacts (the review position, the covenant
record with every failed test named, every breach, the policy
record under both versions, disagreements, the incomplete
section when there is one), and the composer's narrative is
passed through the same figure verifier as the memo — every
figure traces to the pack's pinned inputs. The verifier
recomputes the locked record from those inputs rather than
trusting the candidate: a dropped locked fact, a reworded one,
an invented figure, or a breach denied in prose ("there were no
breaches") are all refused mechanically.

The **review gate** closes the loop. A named reviewer holding a
credit-officer role records the outcome in a coded stance from
the versioned vocabulary `annual-review-reasons-v1` — `affirm`,
`affirm_with_conditions`, `place_on_watchlist`,
`escalate_to_committee` — each with coded reasons; conditions
reuse the committee's machinery whole, so a financial-covenant
condition must trace to a real figure. The officer who approved
the decided memo may not review it alone: their affirmation
needs a countersigning officer, a different person with an
officer role. An escalation mints a **committee referral** in
the same act — a recorded artefact naming the pack, the
outcome, and the decided memo the committee machinery acts on.
An instance closes exactly once; the next year's instance
already stands derived from the anchor.

## The laws (enforced in code, never in prompts)

1. **No model-computed numbers.** Extraction returns values +
   provenance; all math is deterministic code. A memo figure that
   traces to neither is rejected by the memo verifier.
2. **Policy is code, versioned.** Each memo records the policy
   version it was tested under.
3. **Adverse decisions carry coded reasons** (ECOA/Reg B: specific,
   accurate reasons — a model paraphrase is not a reason).
4. **Two human gates** — credit officer, then committee; the
   preparer cannot be the sole approver.
5. **Spreading disagreements surface, never average out** — audited
   vs management vs tax-return figures are all carried, with the
   disagreement named in the memo.
6. **Covenants are clocks + math** — structured test dates and
   thresholds; detection is the agent's job, waiver and enforcement
   are the bank's.
7. **Stale inputs block, visibly** — a memo cannot be marked
   committee-ready over a stale or missing required input; the
   block names the item.
8. **Every draft edit is evidence** — draft-vs-final diffs are
   recorded; the record shows what the machine proposed and what
   the human changed.
